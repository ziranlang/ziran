# Building Ziran's Owned Image Stack

Ziran can reach the owner's **100% authored AVIF/WebP end state** through a staged, modular migration: own the caller-facing image and codec contracts now, use reproducible external engines only as bridges and differential oracles, replace the AVIF container and then AV1/WebP engines module by module, and require current, reproducible measurements before any 10× claim. The 10× figure is a high-priority stretch research target, not a promise: historical 2019–2020 AV1-video charts showed dav1d roughly 2–5× faster than libaom, but they are not current AVIF measurements and do not predict same-core CPU efficiency on 2026 devices ([2019 AOMedia dav1d results](https://downloads.aomedia.org/assets/pdf/symposium-2019/slides/RonaldBultje_TwoOrioles.pdf), [FOSDEM 2020 dav1d results](https://archive.fosdem.org/2020/schedule/event/om_dav1d/attachments/slides/4188/export/events/attachments/om_dav1d/slides/4188/dav1d_1year.pdf)). The immediately credible path is to preserve the current first-frame, straight RGBA8 baseline while profiling it, beat today's deliberately single-threaded libaom configuration under clearly stated conditions, and only then approach current dav1d, libgav1, libaom, browser, and fixed-function hardware paths under equal cores, output, and conformance.

This plan also advances the language without changing its identity. Canonical `.zi` remains the human-readable source of record; checked `.zir` remains the semantic authority. LLM-native work starts with semantic retrieval, bounded diagnostics, exact versioned edits, safe inference, and measured token/correctness evaluation. An optional compact transport can be tested earlier, but a separate concise source face—tentatively called **Zia only for planning**—must use the same parser/checker/IR, renderer, diagnostics, source maps, and tests, and remains deferred until a strong evidence gate passes. Token savings are currently **unmeasured locally** because no tokenizer suite was available.

## Own the boundaries before rewriting the engines

Ziran should not put image codecs in Kryon or make them unconditional standard-library features. Ziran repository rules reserve this repository for language, compiler, `.zir`, portable `.zx`, standard modules, and runtime, and require programs to remain useful without a UI ([Ziran rules](https://github.com/ziranlang/ziran/blob/abb165ca8425337a21220c2538cd5ae9d041af9c/AGENTS.md#L1-L21)). The right package roots are **proposed** sibling repositories under `/mnt/storage/Projects/ziranlang/packages/`: `image-codec` for shared contracts and fixtures, `avif` for AVIF/BMFF and eventually AV1, and `webp` for RIFF/VP8L/VP8. They reuse the existing `std/image.Image`, which is already specified as straight, non-premultiplied, tightly packed, top-to-bottom RGBA8 backed by `Vec(u8)` ([`std/image.zi`](https://github.com/ziranlang/ziran/blob/abb165ca8425337a21220c2538cd5ae9d041af9c/std/image.zi#L1-L22)).

The bridge phase can pin reproducible native artifacts without a vendor-tree edit: Ziran package source dependencies can pin and cache a non-Ziran Git repository, expose it through `ziran pkg path`, and describe native recipes with explicit inputs, outputs, platform identifiers, digests, prerequisites, and link metadata ([package source dependencies](https://github.com/ziranlang/ziran/blob/abb165ca8425337a21220c2538cd5ae9d041af9c/docs/PACKAGES.md#L245-L265), [native artifact recipes](https://github.com/ziranlang/ziran/blob/abb165ca8425337a21220c2538cd5ae9d041af9c/docs/PACKAGES.md#L378-L529)). These bridges are migration oracles and comparison engines, not the destination and not a proposed handwritten C codec. Kryon keeps only backend adapters: cache keys, texture upload, surface conversion, and platform selection. A headless CLI must decode and validate files with **no GUI dependency**.

The present Kryon evidence is a **working-copy snapshot, not a committed or released baseline**: `src/backend/avif_decode.zi`, `src/backend/avif_image.zi`, `cmake/AVIF.cmake`, and related tests are currently in progress and must not be represented as HEAD ([local AVIF decoder](/mnt/storage/Projects/kryonlabs/kryon/src/backend/avif_decode.zi), [local libavif build](/mnt/storage/Projects/kryonlabs/kryon/cmake/AVIF.cmake), [local backend notes](/mnt/storage/Projects/kryonlabs/kryon/docs/BACKENDS.md)). That snapshot describes a deliberately constrained path—locked libavif 1.3 plus libaom, one CPU thread, decode-only libaom, no libaom multithreading, no libyuv/libsharpyuv, and no dav1d/libgav1—while returning the first complete frame as RGBA8 and preserving alpha, crop, rotation, mirror, 8/10/12-bit input, and monochrome within the existing 256 MiB file, 32,768-axis, and 67,108,864-pixel limits. Profiling therefore precedes optimization: the bottleneck cannot honestly be inferred when engine choice, threading, and conversion acceleration are all disabled, and integration must first preserve and validate the active source changes.

## Replace AVIF and WebP in defensible modules

The AVIF package needs a clean split between container and AV1 engine. On the container side, modules must cover ISO-BMFF boxes, item references, properties, clean aperture, orientation, mirrors, grids, alpha association, limits, and extraction of color and alpha OBUs. The output side must own alpha application, chroma upsampling, matrix/range/transfer conversion, allocation, diagnostics, cancellation, and caller-owned RGBA buffers. AVIF is explicitly a HEIF-conformant image format with derived and tone-mapped item relationships ([AVIF v1.2.0 specification](https://aomedia.org/docs/AV1%20Image%20File%20Format%20%28AVIF%29%20v1.2.0.pdf)).

The AV1 engine must eventually own OBU framing, uncompressed headers, range decoding, entropy-coded coefficients, tiles, intra prediction, inter machinery required by the profile, inverse transforms, reconstruction, deblocking, CDEF, loop restoration, and optional film grain. dav1d identifies the same performance-sensitive stages—MSAC, inverse transform, motion compensation, intra prediction, filtering, restoration, CDEF, and film grain—while noting remaining entropy-related C code ([dav1d FOSDEM 2020](https://archive.fosdem.org/2020/schedule/event/om_dav1d/attachments/slides/4188/export/events/attachments/om_dav1d/slides/4188/dav1d_1year.pdf)). Every DSP family gets an authored `.zi` scalar reference first; optimized lowering is accepted only after bit-exact differential tests and machine-code inspection.

WebP is a separately staged engine, not a claim hidden inside AVIF. Milestones are RIFF/VP8L lossless decoding, ALPH alpha, VP8 lossy baseline, animation only after the single-image contract is stable, and encoding as a **future, separately scoped extension**. The initial API can represent still RGBA output while explicitly rejecting unsupported layers rather than partially decoding them.

Shared contracts are as important as bitstream modules. The `image-codec` package must provide bounded bytes/planes, checked integer math, stride and alignment rules, explicit borrowed-versus-owned buffers, zero-copy views where sound, allocation-failure injection, worker limits, cancellation, stable error codes, deterministic metadata, and a fixture manifest with digests and expected output. The current baseline's rejection behavior for truncated containers, invalid crops, and oversized images must remain exact until a named compatibility migration is approved.

## Measure ten-x honestly before chasing it

The target has three different meanings. **Wall latency** may improve by using more workers; **CPU time per pixel** charges all active cores; and **throughput, peak memory, allocation count, and energy** describe different deployment wins. A 10× wall result against one-thread libaom is not a 10× CPU-efficiency result against dav1d under equal active cores. Benchmarks must report p50/p95 latency, CPU-time/pixel, pixels/second, active worker count, peak RSS, allocations, corpus/toolchain versions, cold/warm caches, and hardware. Current libaom, libgav1, and dav1d expose multithreading and broad SIMD families, so “any other decoder” cannot be a universal acceptance target ([libaom defaults](https://aomedia.googlesource.com/aom/+/refs/heads/master/build/cmake/aom_config_defaults.cmake), [libgav1](https://chromium.googlesource.com/codecs/libgav1/+/refs/heads/main/README.md), [dav1d](https://github.com/videolan/dav1d/blob/master/README.md)).

Benchmark both complete file-to-RGBA and isolated kernels. Complete-file tests must use strict output comparison first; engine-only OBU/IVF tests can explain kernels but cannot be labeled full AVIF performance. Color and alpha may run concurrently when independent, while tile parallelism requires enough tiles; a one-tile still image does not magically scale. No global system tuning or unsafe affinity is permitted. AV1 hardware is a separate class of competitor: Android requires baseline AVIF decoding and has AV1 hardware requirements for some performance-class devices, while WebCodecs exposes only a hardware preference, not a guarantee that all AVIF features use fixed-function acceleration ([Android 15 CDD](https://source.android.com/docs/compatibility/15/android-15-cdd), [WebCodecs](https://www.w3.org/TR/webcodecs/#videodecoderconfig-dictionary)).

The compiler track follows the same discipline. Current Ziran emits generated C, generated Go, portable `.zx`, and a WASM subset, with fixed-width scalars, fixed arrays, checked slices, and owned `Vec`; checked GNU `#asm`, CPU guards, and cached dispatch already exist, while packed SIMD IR/compiler intrinsics and proved bounds/alias elimination do not. Therefore compiler work starts with generated-code baselines, ABI/capability metadata, sound check elimination, allocation-free leaf loops, and bounded workers. Packed-vector semantics and intrinsics arrive only when a profiled kernel demonstrates need. Assembly is expressed through checked `.zi` `#asm` or compiler lowering, never promised for every ISA before profiles and validation exist. Current Android ABIs and x86-64/AArch64 desktop are the first targets; RISC-V RVV, POWER, and LoongArch are later, explicitly validated paths.

## Make Ziran native for models without forking semantics

The language track should improve the interface models actually use. First, expose a deterministic, symbol-scoped checked-IR projection containing declarations, signatures, types, effects, ownership, laws, spans, imports, and bounded examples. Second, emit bounded diagnostic facts with stable semantic IDs and exact non-overlapping edit alternatives. Third, add a preview/apply semantic edit command that rejects stale versions, collisions, malformed edits, and changes that fail checking. Fourth, add inference only where there is one checked local answer; public signatures, effects, capabilities, and imports remain explicit contracts. Fifth, add a lossless compact **transport view**, not a commit format, and measure total tokens plus repair correctness across available tokenizer families. The same text can tokenize differently by model and encoding ([OpenAI token guidance](https://help.openai.com/en/articles/4936856-understanding-and-counting-tokens)).

The optional concise face is the owner-requested research direction and remains a measured experiment, not a permission question or a second language. It must expand to canonical `.zi`, share one checker and `.zir`, map every diagnostic to source, preserve laws and portable/native parity, and win both token/correctness and human-review gates before product exposure. It must not fork backend semantics or rename the language prematurely. Human readability is a measured requirement, not an assumption.

## Mega plan: phases, dependency graph, and task contracts

`NEW` marks proposed commands and paths; `EXISTING` marks commands/files already present. Proposed APIs, examples, and syntax are planning targets, not implemented language. Every future compilation or build command must pass through the project build queue as `build-queue -- COMMAND`. Each task requires local integrated validation before any commit; commits and pushes happen only once a complete scoped implementation passes its suite, and the plan deliberately contains no phase, fixture, or milestone commits.

### Critical path and parallelism

The shortest critical path is **C-01 → C-02 → C-03/C-06 → C-07 → A-01 → A-02 → A-03 → V-01 → V-02 → V-03 → V-04/V-05 → V-06 → D-01 → D-05 → Q-01/Q-05 → P-01/P-02**. WebP can proceed on **C-08 → W-01 → K-01 → D-08** after shared contracts, while compiler work begins independently at **D-02 → D-03/D-04 → D-05**. LLM work is independent until codec package APIs and diagnostics need projection; start **L-01 → L-02/L-03 → L-04/L-05 → L-06 → L-07** immediately without blocking image correctness. ARMv7, additional ISAs, animation, HDR/native-depth output, encoding, and Zia all remain evidence-gated and must not preempt first-tier correctness.

## Conclusion

The winning interpretation of “100% Ziran” is ownership of semantics and source, not isolation from evidence. Use current libavif/dav1d/libaom/libgav1/libwebp now as pinned oracles, own container and public API behavior quickly, and replace engines only after fixtures, conformance, memory, and cancellation prove each layer. Assembly and packed SIMD are compiler capabilities derived from measured kernels and guarded dispatch, never a checklist of unsupported promises. The compiler and LLM tracks reinforce this: fewer tokens and faster kernels must both be validated by exact semantics, bounded diagnostics, checked edits, portable parity, and measured repair/output results.

The owner's 10× ambition should remain visible in every benchmark decision, but its acceptance condition must be precise: named corpus, architecture, cores, output depth, color strictness, decoder versions, cold/warm state, latency, CPU time, throughput, memory, allocations, and energy where measurable. Until those data exist, the honest deliverable is a modular owned stack with a credible measurement path—not a fabricated speed claim.
