# Modular AVIF/WebP architecture and migration

## What modules and packages should Ziran own, and what stays out of Kryon?

### Takeaway
Ziran should own the portable image value type, codec API, error/metadata model, fixtures, and platform-independent package boundaries; AVIF and WebP should start as optional `ziranlang` packages backed by reproducible native artifacts, not as Kryon backend files or unconditional `std` modules.

### Cited Findings
- Ziran's repository rules reserve the repository for language, compiler tools, `.zir`, portable `.zx`, standard modules, and runtime, require it to remain useful without a UI library, and forbid Kryon widgets or UI-specific compiler cases. — [Ziran AGENTS.md at `abb165ca`](https://github.com/ziranlang/ziran/blob/abb165ca8425337a21220c2538cd5ae9d041af9c/AGENTS.md#L1-L21)
- Ziran packages are Git repositories pinned in `ziran.lock`; only declared exports are visible, private package modules cannot collide, and package module identities derived from repository and commit survive checked IR, saved `.zir`, portable bundles, and native output. — [Ziran PACKAGES.md at `abb165ca`](https://github.com/ziranlang/ziran/blob/abb165ca8425337a21220c2538cd5ae9d041af9c/docs/PACKAGES.md#L120-L157), [publishing rules](https://github.com/ziranlang/ziran/blob/abb165ca8425337a21220c2538cd5ae9d041af9c/docs/PACKAGES.md#L185-L210)
- A source-only Ziran dependency can pin and cache a non-Ziran C repository, expose its checkout through `ziran pkg path`, and keep it out of a `vendor/` tree; a package project tool can declare native recipes with explicit inputs, outputs, platform identifiers, prerequisites, digests, and link metadata. — [source dependencies](https://github.com/ziranlang/ziran/blob/abb165ca8425337a21220c2538cd5ae9d041af9c/docs/PACKAGES.md#L245-L265), [native artifacts](https://github.com/ziranlang/ziran/blob/abb165ca8425337a21220c2538cd5ae9d041af9c/docs/PACKAGES.md#L378-L529)
- `std/image.Image` is already the canonical in-memory picture: straight, non-premultiplied RGBA8, top-to-bottom rows, no padding, dimensions, and a Ziran `Vec(u8)` pixel buffer; `ImageValid` checks the exact `width * height * 4` length. — [std/image.zi at `abb165ca`](https://github.com/ziranlang/ziran/blob/abb165ca8425337a21220c2538cd5ae9d041af9c/std/image.zi#L1-L22), [validation](https://github.com/ziranlang/ziran/blob/abb165ca8425337a21220c2538cd5ae9d041af9c/std/image.zi#L52-L55)
- Kryon's current working-copy snapshot owns format code in backend files: shared AVIF parsing/conversion in `avif_decode.zi`, static libavif bindings in `avif_image.zi`, static libwebp bindings in `webp_image.zi`, and a dynamic Linux loader in `image_decode_linux.zi`. These files are not yet evidence of a committed Kryon revision. — [avif_decode.zi](/mnt/storage/Projects/kryonlabs/kryon/src/backend/avif_decode.zi), [avif_image.zi](/mnt/storage/Projects/kryonlabs/kryon/src/backend/avif_image.zi), [webp_image.zi](/mnt/storage/Projects/kryonlabs/kryon/src/backend/webp_image.zi), [image_decode_linux.zi](/mnt/storage/Projects/kryonlabs/kryon/src/backend/image_decode_linux.zi)
- Kryon documents the platform split as locked libavif/libaom for native hosts, dynamic system WebP for Cairo, static libwebp for Raylib/Android, and the browser's own codec through `PageImageDecode`. — [local Kryon BACKENDS.md](/mnt/storage/Projects/kryonlabs/kryon/docs/BACKENDS.md)
- libavif's RGB API permits a caller-supplied buffer sized from width, height, row bytes, and pixel size, or its allocate/free convenience pair; this makes a Ziran-owned output allocation the natural ABI boundary. — [libavif 1.3.0 API](https://raw.githubusercontent.com/AOMediaCodec/libavif/v1.3.0/include/avif/avif.h)
- libwebp documents `WebPDecodeRGBA` as returning scan-order RGBA that must be deleted with `WebPFree`, while animation `WebPAnimDecoderGetNext` returns a reconstructed canvas buffer valid only until the next/reset/delete call. — [libwebp decode.h](https://raw.githubusercontent.com/webmproject/libwebp/main/src/webp/decode.h), [libwebp demux.h](https://raw.githubusercontent.com/webmproject/libwebp/main/src/webp/demux.h)
- The current AVIF and WebP container specifications expose more than Kryon's still-first-frame surface: AVIF has image items, image sequences, crop/rotation/mirror properties, and profile brands; extended WebP has ICC, Exif, XMP, alpha, animation, canvas assembly, VP8 lossy, and VP8L lossless chunks. — [AVIF v1.2.0](https://aomediacodec.github.io/av1-avif/v1.2.0.html), [WebP container specification](https://developers.google.com/speed/webp/docs/riff_container)

### Inferences
- Use three package roots rather than expanding unconditional `std`:
  - `ziranlang/image-codec`: package-owned `Codec`, `DecodeOptions`, `DecodeError`, `DecodeMetadata`, sniff traits, and fixture contracts. It imports `std/image` but imports no AVIF, WebP, Kryon, Cairo, Raylib, Android, or browser module.
  - `ziranlang/avif`: exports `AVIF`; privately contains the dependency bridge and, in later stages, the Ziran-owned container/color/AV1 layers. It depends on `image-codec` plus locked `source = true` libavif and libaom packages.
  - `ziranlang/webp`: exports `WebP`; privately contains the dependency bridge and later Ziran-owned RIFF/VP8/VP8L/ALPH/animation layers. It depends on `image-codec` plus a locked source-only libwebp package.
- Separate repositories are preferable to one `std/avif.zi`/`std/webp.zi` because each format can pin only its native dependency graph, publish independent native recipes, change without rebuilding unrelated programs, and keep browser or pure-Ziran users from pulling the other codec. This follows the current package export and native-artifact model rather than requiring a compiler special case. — [package semantics](https://github.com/ziranlang/ziran/blob/abb165ca8425337a21220c2538cd5ae9d041af9c/docs/PACKAGES.md#L120-L210), [native artifacts](https://github.com/ziranlang/ziran/blob/abb165ca8425337a21220c2538cd5ae9d041af9c/docs/PACKAGES.md#L378-L529)
- Keep `std/image.Image` unchanged as the common value. Do not move it to `image-codec`: PNG/JPEG already use it, package identities are designed to survive IR/native output, and moving it would create unnecessary churn across Ziran and Kryon. — [std/image.zi](https://github.com/ziranlang/ziran/blob/abb165ca8425337a21220c2538cd5ae9d041af9c/std/image.zi#L1-L22), [PNG boundary](https://github.com/ziranlang/ziran/blob/abb165ca8425337a21220c2538cd5ae9d041af9c/std/png_linux.zi#L345-L357)
- Stage the end state as “100% handwritten Ziran modules behind a stable package API,” not “no dependencies on day one.” Initially, external libraries are selectable native providers and conformance oracles; each replaced layer must remain reachable for A/B comparison until the Ziran implementation passes the same fixtures. This is consistent with package-owned native artifacts and source-only dependencies. — [source dependencies](https://github.com/ziranlang/ziran/blob/abb165ca8425337a21220c2538cd5ae9d041af9c/docs/PACKAGES.md#L245-L265)
- Kryon should eventually depend only on `image-codec`, `avif`, and `webp`; Kryon may keep backend adapters that copy `Image` into Cairo/Raylib/browser objects, but must no longer own format parsing, native symbols, allocator selection, or codec artifacts. The current working-copy files and build entries identify that exact ownership transfer. — [local Kryon backend notes](/mnt/storage/Projects/kryonlabs/kryon/docs/BACKENDS.md)

### Gaps
- The package documentation shown here documents one `[artifacts.native]` recipe per example; separate AVIF and WebP packages avoid depending on multiple named recipes in one package, but implementation should verify whether multiple recipe names are already supported before considering a combined codec package. — [native artifact model](https://github.com/ziranlang/ziran/blob/abb165ca8425337a21220c2538cd5ae9d041af9c/docs/PACKAGES.md#L378-L390)
- Exact license obligations for each locked source dependency and for any later reference-test-derived implementation need a repository-specific review; no legal conclusion is made here.

## What common ownership, error, metadata, and platform contracts must every caller migrate to?

### Takeaway
The codec API should return an owning Ziran `Image` plus separately owned metadata in a `Result`, apply all declared first-frame transforms before return, centralize limits and diagnostics, and never expose a raw native pointer or an `avif: bool` allocator discriminator to Kryon.

### Cited Findings
- Ziran already has a generic `Result($T, $E)` with explicit `is_ok`, `value`, and `error`; `std/image.Image` owns pixels in `Vec(u8)`. — [std/result.zi at `abb165ca`](https://github.com/ziranlang/ziran/blob/abb165ca8425337a21220c2538cd5ae9d041af9c/std/result.zi#L1-L5), [std/image.zi](https://github.com/ziranlang/ziran/blob/abb165ca8425337a21220c2538cd5ae9d041af9c/std/image.zi#L18-L22)
- Kryon's shared AVIF working-copy path enforces a 256 MiB input limit, 67,108,864-pixel limit, 32,768-axis limit, one thread, ignored Exif/XMP, first complete frame, straight RGBA8, and explicit crop/rotate/mirror handling; malformed, truncated, bad-crop, and oversized inputs fail. — [avif_decode.zi](/mnt/storage/Projects/kryonlabs/kryon/src/backend/avif_decode.zi), [codec fixture](/mnt/storage/Projects/kryonlabs/kryon/tests/avif_codec_test.zi)
- Kryon's Linux `WebPImage` embeds `avif: bool`, and `CloseStill` uses that boolean to choose `AvifFree` versus WebP release; that is the ownership leak the new API must eliminate. — [image_decode_linux.zi](/mnt/storage/Projects/kryonlabs/kryon/src/backend/image_decode_linux.zi)
- libavif surfaces decoder diagnostics, size/dimension/count limits, ignore-Exif/XMP controls, RGBA conversion controls, transformation flags, ICC/CICP/CLLI-related image state, Exif/XMP payloads, and gain-map ownership; its transform values are explicit API state rather than implicitly applied pixels. — [libavif 1.3.0 API](https://raw.githubusercontent.com/AOMediaCodec/libavif/v1.3.0/include/avif/avif.h)
- WebP's extended-format flags and chunks explicitly describe ICC, alpha, Exif, XMP, animation, and canvas dimensions; the animation API returns a full reconstructed canvas whose lifetime ends on the next/reset/delete operation. — [WebP container specification](https://developers.google.com/speed/webp/docs/riff_container), [libwebp demux.h](https://raw.githubusercontent.com/webmproject/libwebp/main/src/webp/demux.h)
- Cairo `ARGB32` is native-endian alpha/red/green/blue with premultiplied alpha, and a caller-owned Cairo data surface can outlive a decoder while requiring Cairo-computed stride; therefore Cairo conversion belongs in Kryon's adapter, not in a generic codec package. — [Cairo image surfaces](https://cairographics.org/manual/cairo-Image-Surfaces.html)
- Kryon's browser path decodes an encoded blob with `createImageBitmap`, draws to canvas, extracts RGBA `ImageData`, copies into malloc-owned memory, caps dimensions at 16,384 and RGBA at 64 MiB, and explicitly closes the bitmap. — [page_texture.zi](/mnt/storage/Projects/kryonlabs/kryon/src/backend/page_texture.zi), [HTML ImageBitmap](https://html.spec.whatwg.org/multipage/imagebitmap-and-animations.html), [HTML ImageData](https://html.spec.whatwg.org/multipage/imagebitmap-and-animations.html)
- Raylib's Kryon adapter recognizes AVIF and WebP before Raylib, wraps returned pointers as Raylib images, and has a single `RaylibImageRelease` that currently calls Raylib unload. — [raylib_image_decode.zi](/mnt/storage/Projects/kryonlabs/kryon/src/backend/raylib_image_decode.zi)
- Cairo currently opens Kryon's still decoder, copies straight RGBA into premultiplied Cairo rows using Cairo stride, closes the decoder's buffer, and only then falls back to GdkPixbuf or Cairo PNG for non-AVIF formats. — [cairo_raster.zi](/mnt/storage/Projects/kryonlabs/kryon/src/backend/cairo_raster.zi)

### Inferences
- The common API should be approximately:

```zi
DecodeOptions :: struct {
    byte_limit: usize = default
    pixel_limit: u64 = default
    dimension_limit: u32 = default
    thread_limit: u32 = 1
    frame: FrameSelection = .FirstComplete
    strict: bool = true
}

DecodeError :: struct {
    kind: DecodeErrorKind
    message: string
    backend: optional string
}

DecodedImage :: struct {
    image: Image
    metadata: DecodeMetadata
}

Decode :: (data: []u8, options: DecodeOptions) -> Result(DecodedImage, DecodeError)
Sniff :: (data: []u8) -> bool
```

  The precise spelling must follow current Ziran optionality/string conventions, but the essential contract is stable: no output pointer arguments, no native allocator choice, no silent fallback, and no caller-visible codec handle for the still-image path.
- `DecodedImage` should own copied pixels in `Image.pixels`. At the bridge boundary, the module supplies or copies into its own storage, destroys the native decoder/handle with its backend-specific function, and returns only `Image`/metadata. This directly removes Kryon's `avif: bool` policy and isolates libavif and libwebp ownership differences. — [std/image ownership](https://github.com/ziranlang/ziran/blob/abb165ca8425337a21220c2538cd5ae9d041af9c/std/image.zi#L18-L22), [libavif buffer model](https://raw.githubusercontent.com/AOMediaCodec/libavif/v1.3.0/include/avif/avif.h), [libwebp ownership](https://raw.githubusercontent.com/webmproject/libwebp/main/src/webp/decode.h)
- Preserve current defaults as one named profile, likely `StillCompatible`: first complete frame, straight RGBA8, one thread, 256 MiB encoded bytes, 67,108,864 pixels, 32,768 per dimension, Exif/XMP retained as metadata but not interpreted as hidden orientation, and AVIF `clap`/`irot`/`imir` applied to the returned image. Add a `Metadata.transforms_applied` field rather than making callers guess. — [current local Kryon policy](/mnt/storage/Projects/kryonlabs/kryon/src/backend/avif_decode.zi)
- `DecodeMetadata` should be format-neutral and own copied bytes for ICC, Exif, and XMP. Common scalar fields should include source bit depth, alpha presence, color primaries/transfer/matrix/range, ICC presence, CLLI when available, animation/canvas/frame/timing summary, gain-map presence, codec identity, and raw transform values alongside `transforms_applied`. This avoids pretending RGBA8 is lossless metadata while leaving HDR display policy to a later explicit API. — [libavif API](https://raw.githubusercontent.com/AOMediaCodec/libavif/v1.3.0/include/avif/avif.h), [WebP container](https://developers.google.com/speed/webp/docs/riff_container)
- Error kinds should distinguish unsupported format, malformed container, truncated stream, byte/dimension/pixel/frame limit, unsupported feature, allocation failure, and provider failure; provider diagnostics must be copied before native destruction. This is a direct replacement for today's null-only failures and maps naturally to `Result`. — [std/result.zi](https://github.com/ziranlang/ziran/blob/abb165ca8425337a21220c2538cd5ae9d041af9c/std/result.zi#L1-L5), [libavif diagnostics](https://raw.githubusercontent.com/AOMediaCodec/libavif/v1.3.0/include/avif/avif.h)
- Platform adapters should be Kryon-owned because they own backend object lifetime:
  - Cairo: `Image` → `cairo_image_surface_create` or caller surface, straight-to-premultiplied conversion, Cairo stride, surface destroy.
  - Raylib/native: copy or transfer `Image.pixels` into Raylib's image representation and unload through one adapter close.
  - Browser: initially preserve `createImageBitmap`/Canvas2D/`ImageData`; make it implement the same Ziran `Codec` adapter and compare shared fixtures rather than forcing a native decoder into Wasm before artifact size and support are known.
  - Android: link package-provided static artifacts per ABI and run the same decode API; do not infer OS codec availability from the Android version.
  These boundaries are justified by Cairo stride/premultiplication, browser bitmap ownership, and current Raylib/Cairo integration. — [Cairo manual](https://cairographics.org/manual/cairo-Image-Surfaces.html), [HTML ImageBitmap](https://html.spec.whatwg.org/multipage/imagebitmap-and-animations.html), [local Kryon adapters](/mnt/storage/Projects/kryonlabs/kryon/docs/BACKENDS.md)
- Every affected caller must migrate, not only the Raylib path: `src/backend/cairo_raster.zi`, `src/backend/image_decode_linux.zi`, `src/backend/raylib_image_decode.zi`, `src/backend/page_texture.zi`, `src/backend/canvas_texture.zi`, and image preview/background-loading tests that call these boundaries. A direct scan of the current local Kryon working copy found these paths. — [Cairo](/mnt/storage/Projects/kryonlabs/kryon/src/backend/cairo_raster.zi), [Raylib](/mnt/storage/Projects/kryonlabs/kryon/src/backend/raylib_image_decode.zi), [browser](/mnt/storage/Projects/kryonlabs/kryon/src/backend/canvas_texture.zi)

### Gaps
- Native-depth/HDR and encoding are not specified by the current Kryon surface; this architecture should expose metadata truthfully but must not silently overload RGBA8 goldens with HDR semantics.
- Animation playback semantics are also outside the current still-image contract. A future frame iterator should be a separate API; `FirstComplete` should remain explicit and observable.
- Browser color management can differ from native CPU conversion even when bytes are extracted as RGBA; fixtures need tagged color-space behavior and declared tolerances before exact cross-backend equality can be required.

## What staged migration and acceptance gates should implement the bridge and eventual full ownership?

### Takeaway
Migrate in four reversible stages—shared contract/fixtures, external-library package bridge, Kryon caller migration, then layer-by-layer Ziran replacement—with source/saved-IR/portable, native, browser, Android, ownership, and metadata gates before removing any Kryon codec path.

### Cited Findings
- Kryon's current working-copy build compiles backend `avif*.zi` files for host sources, adds `image_decode_linux.zi` and `avif_decode.zi` to desktop, links WebP with Raylib, and links Android Raylib publicly against `kryonwebp`, `avif`, and `aom`. — [mk/ziran-project.mk](/mnt/storage/Projects/kryonlabs/kryon/mk/ziran-project.mk), [Android CMake](/mnt/storage/Projects/kryonlabs/kryon/cmake/KryonAndroid.cmake)
- Existing gates already cover native source/saved-IR AVIF goldens, Cairo and private-display Raylib rendering, browser behavior, all-ABI Android AVIF, native WebP, WebP browser behavior, and background image decode; browser commands scrub `DISPLAY`, `WAYLAND_DISPLAY`, `XAUTHORITY`, and session variables. — [local BACKENDS.md](/mnt/storage/Projects/kryonlabs/kryon/docs/BACKENDS.md), [Makefile](/mnt/storage/Projects/kryonlabs/kryon/Makefile)
- Current working-copy AVIF fixtures cover RGBA8/10/12, gray8/10/12, six crop/rotate/mirror combinations, premultiplied alpha, opaque and animated input, extensionless assets, plus oversized, pixel-limit, bad-crop, truncated, and malformed rejection. — [avif_codec_test.zi](/mnt/storage/Projects/kryonlabs/kryon/tests/avif_codec_test.zi)
- Existing source, saved-IR, and golden-pixel checks exercise the same decoder through source paths and saved assets, including `assets/image.avif`, PNG-equivalent paths, and extensionless names. — [avif_codec_test.zi](/mnt/storage/Projects/kryonlabs/kryon/tests/avif_codec_test.zi), [decode test](/mnt/storage/Projects/kryonlabs/kryon/tests/avif_decode_test.zi)
- Package artifact identity includes the locked graph, checkout heads, launcher/compiler bytes, platform/ABI, recipe/input bytes, options, prerequisite descriptors, compiler identity, and relevant native environment, and clean dirty checkouts are required for reuse. — [PACKAGES.md at `abb165ca`](https://github.com/ziranlang/ziran/blob/abb165ca8425337a21220c2538cd5ae9d041af9c/docs/PACKAGES.md#L447-L538)

### Inferences
- **Stage 0—contract and oracle freeze.** Before implementation, define a versioned fixture manifest and expected metadata/pixel tolerance map in `image-codec`; it is committed only with the first complete scoped implementation that passes its integrated local tests, not as an early milestone commit. Reuse and extend the AVIF matrix above; add WebP lossy, lossless, alpha, animated-first-frame, ICC/Exif/XMP, malformed/truncated, odd-sized RIFF chunks, and limit cases. Every fixture needs content hashes and a small golden or semantic assertion. The performance track owns detailed speed corpora; this gate is correctness and API stability. — [existing fixture model](/mnt/storage/Projects/kryonlabs/kryon/tests/avif_codec_test.zi)
- **Stage 1—package bridge.** Create `ziranlang/image-codec`, `ziranlang/avif`, and `ziranlang/webp`; each format package exports exactly one public codec module and privately contains FFI/provider modules. Add source-only locked dependencies and `[artifacts.native]` recipes for current targets. Initially produce at minimum: Linux x86_64 shared for Cairo, Linux native static for Raylib, and the four Android ABIs used by Kryon. The package API must pass all Stage 0 fixtures before Kryon changes.
- **Stage 2—parallel integration.** Add Kryon adapters behind its existing backend interfaces without deleting current paths. Cairo calls the package decoder and owns Cairo surface lifetime; Raylib calls it and owns Raylib image lifetime; browser remains on its native browser adapter. Build links should come from package `link.txt`/artifact metadata rather than Kryon's private source archives. Fail closed for recognized but unsupported AVIF/WebP so GdkPixbuf/Raylib cannot bypass package limits. — [current fail-closed rationale](/mnt/storage/Projects/kryonlabs/kryon/src/backend/image_decode_linux.zi), [artifact link model](https://github.com/ziranlang/ziran/blob/abb165ca8425337a21220c2538cd5ae9d041af9c/docs/PACKAGES.md#L499-L529)
- **Stage 3—Kryon cleanup.** After every target passes, remove Kryon codec ownership from `src/backend/avif_decode.zi`, `src/backend/avif_image.zi`, `src/backend/webp_image.zi`, and the codec-specific parts of `src/backend/image_decode_linux.zi`. Update `Makefile`, `mk/ziran-project.mk`, `mk/raylib-library.mk`, `mk/zx-raylib.mk`, `cmake/AVIF.cmake`, `cmake/WebP.cmake`, and `cmake/KryonAndroid.cmake` to consume package artifacts. Do not remove files while any direct import remains.
- **Stage 4—Ziran-owned stack.** Replace external components incrementally while keeping the same API and fixtures: WebP RIFF/demux metadata first, then VP8L lossless, ALPH, VP8 lossy, and animation composition; AVIF ISO-BMFF/HEIF parsing and color/transform logic before the AV1 engine; finally the AV1 engine kernels. Make the old library a selectable oracle until each layer has its own malformed-input, conformance, and golden suite. This ordering gives independently testable ownership without coupling container correctness to engine-performance work. — [AVIF container/engine split](https://aomediacodec.github.io/av1-avif/v1.2.0.html), [WebP chunk split](https://developers.google.com/speed/webp/docs/riff_container)
- **Mandatory acceptance gates for later implementation**:
  - Package-only unit gate: source, checked/saved IR, native C, and portable VM where FFI is not required; exact pixel bytes or documented existing tolerance.
  - Memory/ownership gate: allocator-neutral `Image`; no raw foreign pixel pointer escapes; native handle close in every success/failure path; repeated decode, cancellation, and background-thread tests have no leak or use-after-free.
  - Metadata/error gate: every fixture reports the declared metadata and one stable error kind; null-only failures are not accepted.
  - Cairo gate: existing image, cache, sampling, scaling, widget, and render tests pass with no display environment.
  - Raylib/native gate: static artifact links and source/saved-IR/golden tests pass, including extensionless assets.
  - Browser gate: browser-native adapter passes existing AVIF/WebP behavior and shared semantic fixtures with explicit color tolerance; a Wasm package decoder is optional until artifact size and support are measured.
  - Android gate: all existing ABIs link the package artifact, and device tests exercise golden pixels and background loading; no installed build is declared from a link-only result.
  - Reproducibility gate: clean locked graph builds the same native artifact descriptors on two invocations; dirty local graphs must not silently claim cache identity. — [artifact identity rules](https://github.com/ziranlang/ziran/blob/abb165ca8425337a21220c2538cd5ae9d041af9c/docs/PACKAGES.md#L447-L538)
- Reuse the existing commands as future integration entry points, adapted to the new package artifacts: `make image-decode-test`, `make raylib-webp-decode-test`, `make avif-decode-test`, `make avif-browser-test`, `make avif-render-test`, `make android-webp-link-test`, `make android-avif-test`, and the current headless WebP browser target. Each compilation must run through `build-queue`. These commands are specifications for later work, not commands run during this research task. — [Makefile](/mnt/storage/Projects/kryonlabs/kryon/Makefile)
- Any efficiency claim must be a measurable hypothesis attached to a fixed corpus, architecture, ABI, core count, cache state, compiler/toolchain, and report metric. A valid “10x” gate must state the baseline and candidate versions and report p50/p95 end-to-end AVIF-to-RGBA latency, throughput, peak memory, failures, and output tolerance. No result is claimed in this architecture note; the dedicated AVIF performance track owns the corpus and measurements.

### Gaps
- Exact Windows/macOS artifact names and toolchains are not established by the current Kryon paths; adding them requires new provider platform validation rather than reusing Linux/Android assumptions.
- It is not yet known whether browser builds can afford a full native codec artifact or a pure-Ziran Wasm decoder; size, codec support, startup latency, and memory must be measured before replacing `PageImageDecode`.
- A pure-Ziran replacement needs format conformance suites beyond the current product fixtures; the source specifications identify the surface, but implementation must select and version specific conformance corpora.
- Exif orientation interpretation is deliberately not proposed as hidden behavior here. Whether image preview should continue browser-like upright presentation or expose raw orientation plus an explicit upright option is a product decision requiring its own fixtures.
